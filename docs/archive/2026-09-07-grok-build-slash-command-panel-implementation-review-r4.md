## 2. 剩余问题

### U1 · P1：同值跳读及无后续触发会永久保留陈旧确认值，不能称为有界收敛

**位置：方案 §6.2.3 第 449–455、483–486 行，§6.2.2 第 423–424 行，§10。**

方案规定每条通知触发权威读，但紧接着又允许 `confirmedMode == 通知声称值` 时跳过读。通知值不是文件版本，显示缓存相等不能证明文件没有变化。去重只能减少通知处理，不能凭值相同取消必要的权威验证。

更直接的失败序列，不需要跨进程并发或无限写盘延迟：

| 时点 | 文件 | 通知/验证行为 | 显示 |
| --- | --- | --- | --- |
| 初始 | default | 已读过 | default |
| 外部进入 plan | 尚为 default | CMU(plan) 先到，开始验证窗口 | default/pending |
| 验证窗口结束 | 仍为 default | 读窗口结束，现稿采用文件旧值 | default |
| 窗口结束后很短时间 | plan | 异步持久化完成，没有新 CMU | 仍 default |
| 会话持续空闲 | plan | 没有下一通知、重开或事务 | 可一直停在 default |

这是**有限的落盘延迟导致无界的显示延迟**，并不要求“写盘延迟无界”。P7 用有限次样本校准 2 秒或其他窗口，不能证明所有调度/磁盘情况下都不会略晚于窗口。现稿把这称为“有界收敛延迟”不成立。此时又到达一条声称 default 的旧通知，本应触发读取 plan；同值跳读却会直接丢掉这次修正机会。

源码支持：上游 `xai-grok-shell/src/session/acp_session_impl/session_mode.rs:44` 更新 actor 后分别 enqueue persistence/CMU；同文件 `:395` 只发送 persistence 消息；`session/persistence.rs:1945` 异步写盘，并不承诺写完再发送一条 CMU。这一异步前提也已被方案 §4.3 接受。

**必须修订：**

1. 删除仅按 `confirmedMode == 通知值` 跳过验证读的规则。可以合并同一轮待处理触发，但必须保证至少一次合并后的权威读，且读过程中产生的新变更不会被清掉。
2. 区分“最近读到的值”和“尚有变化未确认”。窗口内未确认时结束 RPC 等待可以报错，但不能同时把旧缓存继续当作无需验证的当前模式。
3. 明确独立于下一次用户操作的失效/复查入口，例如权威文件变化监听或对未解决状态的有界复查。复查仍无法确认时显示 unknown、禁止切换，不保持一个无限期陈旧的确认值。**复查是读，不得自动重发 set_mode。**
4. 删除“超时后显示停留文件现值”的不准确说法：未再次读取时，它只是上次读取值，之后可能已不是现值。

**关闭测试：**固定验证窗口为 W，令官方写入在 W+ε 完成，此后不发任何通知、不重开会话；必须由设计中的失效/复查机制发现新值，或保持明确 unknown，不得将旧值无限期显示为当前确认值。另测缓存等于通知值而文件已不同，仍执行必要验证。

### U2 · P1：冷 hydrate 仍把未证实持久成功的 CMU 历史当权威来源

**位置：方案 §6.2.3 第 472–476 行、P8，以及“confirmedMode 唯一写者 = 权威读”的总规则。**

冷恢复的来源链仍是 `summary.json mode → plan_mode.json → updates.jsonl 最后一条 CMU`。最后一项并不是读取当前持久模式，而是在重放已被 T1/T2 降级的通知。将它从 JSONL 文件里读出来，不会提升为 plan_mode.json 的持久确认。

反例：上游 actor 进入 plan，CMU(plan) 已写到 updates.jsonl，但 PlanModeState 写盘失败。此后冷 hydrate 读不到 plan_mode.json，按回退链采用最后 CMU(plan)，便会显示已确认 plan；下一 actor 却不能从模式快照恢复这个值。于是冷路径重新制造了 T1 禁止的成功假象。

源码依据：`acp_session_impl/updates.rs:348` 的通知入队与 `session_mode.rs:395` 的模式持久化是独立路径；`session/persistence.rs:1945` 的模式写盘失败仅记 warning。**事件已持久化不等于模式快照已持久化。**

`summary.json` 也不能只因“存在 mode 字段”就优先使用：P8 还要证明它与 spawn 恢复源的更新语义一致。字段存在性是格式证据，不是当前值权威性证据。

**必须修订：**

1. 事务确认、通知验证、冷 hydrate、重订阅共用同一条已验证权威读取契约。P7/P8 可以确定目标版的等价官方来源，但不是运行失败后依次降级的三选一。
2. 删除 CMU 历史作为 `confirmedMode` 直接来源的兜底。CMU 历史可以用于诊断或触发权威读；权威读失败则 unknown，不能借历史值掩盖失败。
3. 将 P8 完成标准从“summary 有没有字段”提升为“该字段是否是与 spawn 一致的可靠当前状态”；不能证明则不用作确认来源。
4. 对文件缺失、损坏、读取错误分别定义返回结果；只有官方明确规定缺失等于默认模式且得到核验时，才可按该语义处理，否则 unknown。

**关闭测试：**updates.jsonl 末尾为 plan，但模式快照缺失/损坏；不得显示确认 plan。再测 summary 与模式快照不一致，必须按确定的唯一权威来源处理，不依返回顺序选择有值的文件。

## 3. 一处需同步澄清的错误分类（不另列阻断项）

§6.2.2 将“持续读到非 requested”解释为“被外部覆盖”。仅凭值不同，不能区分外部覆盖、自有持久化尚未完成或写盘失败。应返回“持久化未确认，最后读到 X”；只有额外证据能确认外部写入时才使用“被外部覆盖”。这不改变三态设计，也不要求添加新的补偿写入。

## 4. 建议的最小统一规则

为避免下一轮继续分别修补冷热路径，正文可以统一成以下契约：

- 所有最终显示值只来自同一个已验证的模式读取函数；通知和旧 RPC 结果都不提供最终值。
- 通知使状态需要重新验证；同批触发可以合并，但值相等不取消读取义务。
- 权威读成功后才能更新最近确认值；存在未解决变化或读失败时，UI 使用 pending/unknown，不能把历史缓存当当前确认值。
- 短窗口限制 RPC 等待时间，不自动构成显示收敛保证；窗口结束后的文件变化由独立失效/复查路径捕获。所有复查只读，绝不自动重发模式切换。
- 冷启动与重新订阅使用同一读取契约；没有已验证权威来源就 unknown，不使用通知历史补成功。

D1–D4 无需重议。修订范围可收敛到上述模式读取与失效契约，T3 不再打开；随后按原有 Phase 0 门验证目标版即可。本轮没有启动需要模型调用或 owner TUI 配合的探针。
