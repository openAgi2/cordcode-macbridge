# “远程访问”界面重构设计方案第二轮评审

> 评审对象：[remote_access_design_proposal.md](../remote_access_design_proposal.md)  
> 上一轮评审：[remote_access_design_proposal_review.md](remote_access_design_proposal_review.md)  
> 评审日期：2026-06-19  
> 评审视角：资深 iOS / Apple 平台交互设计 + 当前实现能力复核

## 一、结论

**新版已经解决上一轮最核心的信息架构问题，方向明显成熟；但“全部意见均已采纳、可以直接实施”的结论仍然过早。**

分组层级、Toggle 位置与语义、安全文案、动效克制和敏感信息边界均已得到有效修正。当前剩余问题主要集中在“诚实状态模型”与真实接口能力仍未完全对齐：

1. 方案仍展示当前 `/internal/remote/status` 无法提供的 Relay 连通状态；
2. 保存流程遗漏“正在应用 / Bridge 重启 / 应用确认”，把 provisioning 与验证混成一步；
3. 仍允许公网 `ws://`，但删除了现有产品中的未加密风险警告；
4. “未检测到 Tailscale 客户端”超出了接口能够证明的事实；
5. 左栏状态摘要仍混合“可用性”和“是否加入新配对”两个维度。

**第二轮结论：有条件通过。完成下述 P0 修订后，可进入实现。**

## 三、阻塞实施的问题

### P0-1：Relay“连通状态”仍属于当前接口不存在的数据

方案在左栏和详情区定义了：

- `可用`
- `连接失败`
- `正在检查…`

但当前 `GET /internal/remote/status` 的注释明确说明：**只读取本机配置，不向外部发起探测**。该接口中的 Relay 数据只有：

- `configured`
- `endpoint`
- `routeId`

Mac 端 `RemoteStatus.RelayStatus` 也只解码上述字段。它不能支持方案中的 Relay 连通状态。

虽然 go-bridge 内部另有包含 `connected`、`lastConnect`、`lastError` 的 `RelayStatus`，但这些字段当前没有通过此页面使用的管理接口暴露。因此文档第 60—62、78—80、131 行仍与“只显示真实 API 数据”的声明矛盾。

**修订方式二选一：**

1. **不改接口：** Relay 只显示 `已配置 / 需要配置 / 状态未知`，不显示“可用、连接失败、正在检查”；
2. **扩展接口：** 明确列出新增 `connected`、`lastConnect`、`lastError` 等字段，并定义它们的刷新、未知态与错误态语义。

不能把“已配置”推导为“可用”，也不能把一次配置失败冒充持续连通状态。

### P0-2：保存流程仍不是完整事务

上一轮要求的流程是：

`有未保存更改 → 正在验证 → 正在应用 → 已保存 / 应用失败`

新版流程仍是：

`未保存 → 正在验证 → 保存成功 / 保存失败`

这遗漏了真实运行路径中的关键阶段：

- 自定义 Relay 保存后需要 provisioning；
- 配置变更会触发 Bridge 重启；
- VPS / FRP 保存当前只有格式校验，并没有真实网络健康检查；
- “配置已写入”不等于“新配置已生效”。

因此“正在验证…”和“保存成功（2 秒后归于未修改）”会制造错误确定性。

**建议按真实能力拆分：**

```text
未修改
  → 有未保存更改
  → 正在校验格式
  → 正在应用配置
  → Bridge 正在重启
  → 已应用
```

失败至少区分：

- 地址格式错误；
- Relay provisioning 失败；
- 配置已保存但 Bridge 重启失败；
- 状态刷新失败，暂时无法确认是否生效。

如果 VPS / FRP 不做网络探测，按钮文案和反馈只能写“正在保存 / 已保存”，不能写“正在验证连接 / 连接可用”。

### P0-3：公网 `ws://` 风险提示被遗漏

方案允许自定义地址使用 `wss://` 或 `ws://`，但没有保留现有界面对公网 `ws://` 的未加密警告。

当前后端已经提供：

- `remoteAnalysis.isPublicWS`
- `remoteAnalysis.securityLevel`
- `remoteAnalysis.hostCategory`

现有本地化文案也明确指出公网 `ws://` 数据未加密。新版若只做格式合法性检查，会让一个“格式合法但安全性差”的地址安静通过。

**修订建议：**

- `wss://`：正常保存；
- Tailscale / 局域网内的 `ws://`：按现有安全分类展示；
- 公网 `ws://`：允许与否由产品策略决定，但至少必须显示持久、明确的高风险警告；
- `https://` 是否自动规范化为 `wss://`，应与现有 `BridgeRemoteURLFormatter` 行为保持一致并写入方案。

## 四、重要但不阻塞架构的问题

### P1-1：不能由空 URL 推断“Tailscale 客户端未运行”

当前接口只返回 `tailscaleURL`，空值只能证明：

**“当前没有可发布的 Tailscale 连接地址。”**

它不能区分：

- 未安装 Tailscale；
- 客户端未运行；
- 未登录；
- 没有分配 IP；
- TLS 候选生成失败；
- 当前产品配置不允许发布该候选。

因此“未检测到客户端”“客户端正在运行”等文案仍然过度推断。

建议统一为：

- `已检测到 Tailscale 地址`
- `未检测到可用的 Tailscale 地址`

如需精确区分安装与运行状态，必须增加独立诊断字段。

### P1-2：左栏摘要仍混合不同状态维度

局域网和 Relay 展示“可用性”，Tailscale 和自定义地址却优先展示“会加入新配对”。四行仍不可直接比较。

建议左栏主状态统一显示路径本身的状态：

- 局域网：`可用 / 不可用 / 状态未知`
- Relay：`已配置 / 需要配置 / 状态未知`
- Tailscale：`地址已检测 / 无可用地址`
- 自定义地址：`已配置 / 尚未配置`

“会加入新配对”作为右栏设置，或在左栏使用弱化的次级 Badge，不应取代路径状态。

另外，绿色只应代表确认可用；“会加入新配对”是设置值，不应使用绿色成功灯。

### P1-3：局域网地址不是“公网安全地址”

文档第 74 行将 `ws://[本机局域网IP]` 称为“公网安全地址”，这是概念错误：

- 它是局域网地址，不是公网地址；
- `ws://` 本身不提供 TLS；
- 它之所以可接受，是因为产品将其限定在可信局域网直连场景，而不是因为地址本身“安全”。

建议改为：

> 局域网连接地址，可复制用于诊断或手动连接。仅应在可信局域网内使用。

“屏蔽本地敏感网络接口细节”也没有必要：展示当前实际使用的局域网连接地址即可，不展示额外网卡列表。

### P1-4：Toggle 前置条件失效后的状态没有定义

假设用户已经打开“配对时提供此连接方式”，随后 Tailscale 地址消失或自定义地址被清空：

- Toggle 是保持开启但禁用，还是自动关闭？
- 左栏显示“会加入新配对”还是“无可用地址”？
- 新生成配对是否实际包含该路径？

当前运行时会过滤空 URL，因此即使 include flag 为 true，空地址也不会进入配对候选。设计应诚实表达这种状态。

建议：

- 保留用户偏好，不擅自关闭；
- 控件显示开启但不可用，并标注“当前无可发布地址”；
- 左栏主状态显示地址不可用；
- 新配对不会包含空候选；
- 地址恢复后自动重新按用户偏好加入新配对。

若产品选择自动关闭，也必须明确说明这是一次设置变更，而不是静默修改。

### P1-5：窄窗口方案需要补全导航行为

“小于 680pt 自动折叠”给出了尺寸规则，但尚未定义单栏状态下：

- 默认进入列表还是保留当前详情；
- 如何返回通道列表；
- 窗口跨阈值变化时是否保留选中项和未保存输入；
- 正在编辑时缩窄窗口是否丢失表单状态。

建议把验收标准写为：布局切换不丢失选择、焦点、未保存输入和错误信息。具体采用 `NavigationSplitView` 还是条件化 `NavigationStack` 属于实现选择，不应在设计文档中承诺两者会自动等价。

## 五、文档表述与可实施性修订

1. 删除“全盘采纳全部建议，无不采纳项”的绝对声明，改为可核查的修改清单。
2. 将“完美支持 Reduce Motion”改为“遵循 Reduce Motion；开启后关闭非必要动画”。“完美”不是可验收标准。
3. “只显示和复制 endpoint IP/域名”应改为“只显示经确认可公开的完整连接 endpoint”。WebSocket 路径和端口可能是连接必需部分，不能一概裁成 IP / 域名。
4. `Publish in new pairing` 不必出现在中文界面正文中；若是本地化 key 或英文稿要求，应单独列出。
5. 明确“刷新状态”保留旧值，并用局部 `ProgressView` 标识刷新中；刷新失败后展示“上次状态 + 更新时间”，不要把旧状态改写成失败。

## 六、修订后的实施门槛

进入实现前需要完成：

1. 删除当前接口无法支持的 Relay 连通状态，或明确新增接口字段；
2. 保存状态机补充“应用、重启、应用确认”阶段；
3. 恢复公网 `ws://` 的安全风险规则；
4. 将 Tailscale 文案收敛到接口确实能证明的“地址是否存在”；
5. 统一左栏主状态维度，将“加入新配对”降为次级设置；
6. 修正局域网地址的安全表述；
7. 定义前置条件消失时 Toggle 与新配对候选的行为；
8. 补充窄窗口切换时的状态保持要求。

完成上述 P0 项后，方案的信息架构可视为通过；完成 P1 项后，可作为足够明确、不会迫使开发者自行猜测关键交互的实施规格。
