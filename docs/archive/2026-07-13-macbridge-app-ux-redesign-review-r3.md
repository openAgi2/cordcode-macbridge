## 4. 实施期注意事项（非阻塞，供实现者参考）

以下 3 点在方案现有框架内有自然答案，**不要求再次修订报告**，仅提醒实现者落地时
遵循，避免把"方案没逐字写"误解为"方案没定义"。

### 4.1 配对组件的复用边界

- **涉及**：L106（工作站首次使用引导的"添加 iPhone 或 iPad"）、L110（设备页
  顶部"添加设备"按钮）、L112-124（配对工作区结构）。
- **方案立场**：两处"添加设备"入口应打开**同一个**配对工作区 / Sheet（L110
  描述的"聚焦工作区或 560–640pt 宽 Sheet"）。
- **实现提醒**：P1 落地时，`WorkspaceView` 的首次使用引导按钮与 `DeviceWorkspaceView`
  的顶部按钮应复用同一配对组件实例或同一触发路径，不要实现成两套独立配对 UI。
  这与方案"组件按产品区域拆分"（L218）不矛盾——拆的是承载页面，复用的是配对
  状态机与工作区组件。

### 4.2 配对 Sheet 的触发位置

- **涉及**：L110"在当前页的聚焦工作区或 560–640pt 宽 Sheet 中承载它"。
- **方案立场**：给出了"聚焦工作区"和"Sheet"两种承载方式，未强制选其一。
- **实现提醒**：P1 可根据 SwiftUI 实现成本二选一。若选 Sheet，注意 macOS
  `.sheet` 默认模态；若选同页聚焦工作区（非模态），需保证用户在配对过程中仍能
  看到设备列表上下文。这是实现细节，方案不要求预先决定。

### 4.3 `[重新检查]` 动作归属

- **涉及**：L88-89（工作站"需要留意"段的 `[重新检查]` 按钮）。
- **方案立场**：L104 已规定"异常状态可在原因旁直接给出'连接状态'动作"——
  `[重新检查]` 属于同一模式的行内修复 CTA。
- **实现提醒**：`[重新检查]` 的语义是"重新探测该 backend / 该连接的健康状态"，
  复用 `BridgeStatusViewModel` 现有的刷新能力（第一轮已确认该 VM 持有 `agents`、
  `relayConfigured` 等状态）。实现时把它接到既有刷新路径即可，不需要新造一个
  诊断动作。这不与 P0.5"保持 `BridgeStatusViewModel` 运行状态职责不变"冲突——
  刷新本就是该 VM 既有职责。
