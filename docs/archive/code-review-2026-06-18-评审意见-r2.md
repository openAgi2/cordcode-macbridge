### 1.2 闭环且额外加分 🌟（3 项）

这几项超出了 R1 的要求，体现了作者的独立深度：

1. **P1-7 手动配对码枚举（新增 P1）**——这是 v2 最有价值的新发现。我核实了源码：
   - `pairing_session.go:302-311`：`generateManualCode` 确实是 6 位纯数字（熵 ≈ 19.9 bit，报告说"约 20 bit"准确）。
   - `pairing_handler.go:171-177`：确实允许 `acceptedManualCode != ""` 单独走 `GetByManualCode` 查找，不要求 pairing ID。
   - pairing WebSocket grep 全文无 `SetReadLimit`/read deadline，"claim 前无读帧上限"成立。
   - 定级 P1 恰当：攻击者 B（同 LAN 未配对）即可发起，虽最终需 Mac 审批，但"抢先 claim + DoS + 伪造设备名诱导误批"是真实危害，不能因"还要审批"就降级。

2. **§5.1 prekey 专项的"不采纳"论证**——这是整份报告**最体现技术诚实**的地方。R1 我提出"prekey 批量端点可撑爆 Relay 表"，作者没有为了显得"全面采纳"而硬塞一个漏洞，而是实际 grep 了 `relay-server` 全目录（我复核：`prekey` 在 relay-server 零命中），确认 Relay 根本没有 prekey 表/端点，prekey 是 go-bridge inner RPC（`relay_prekey.go`），且单设备硬上限 64（`:29`）。然后只保留了一个真实的中低风险观察（`processedBatches map` 无清理，`:112`/`:215`）。**这种"我的假设错了，我明确说出来"的态度，比堆砌漏洞更有价值。**

3. **§5.2 mailbox 专项的精确归因**——核实 `server.go:528-541`，mailbox append 确实只在 bridge socket 读循环、校验 `KeyEpochID` 前缀和 `DestinationID`，device socket 不能写 mailbox。作者据此把"普通 device 灌垃圾"驳回、把风险精确收敛到"route credential 泄漏者 D + buggy bridge"，归因非常干净。

### 1.3 需说明的"部分采纳"（1 项）

**P1-3 复用 `core.AtomicWriteFile`——部分采纳。** 采纳矩阵写的"可复用其思路和代码；现有原语仍缺目录 fsync/提交前内存快照，不能只机械替换"。这个判断**比我 R1 的建议更严谨**——我 R1 说"直接走 core.AtomicWriteFile"，但作者指出该原语缺目录 fsync 和内存快照原子性。我核实认可这个反驳（见 §3.1，这也说明 R1 我那条建议本身略粗糙）。这是"部分采纳且反驳有据"，属于健康讨论。

## 2. 新增内容评审

### 2.1 §2 威胁模型 —— 质量高，一个小建议

攻击者 A-E 的画像清晰，且后续每条的定级都确实回扣了这五类（如 P2-8 显式说"需要攻击者 E 的本地落点"）。这解决了 R1 的首要结构问题。

**小瑕疵**：威胁模型里缺一个**横截面说明**——攻击者 C（已配对失陷设备）和 D（route credential 泄漏）的**前置获取成本差异很大**，但表格里并列呈现，读者容易等权看待。建议在表格下补一句："C 的门槛是设备物理/逻辑失陷（中等），D 的门槛是 route credential 泄漏（需 Mac 侧额外失陷，较高）；定级时 C 类问题权重更高。"这不影响整改，纯属表述精度。

### 2.2 §5 Relay 专项 —— 准确且有深度，是 v2 最大增量

§5.1/5.2/5.3 三条复核，每条都做到了"先验证代码事实，再决定采纳/不采纳/降级"，且引用精确到行。特别是 §5.3 对 activation 竞争的结论（install_id 主键 + signing pubkey 唯一约束 + 事务保护，未发现 identity 替换竞态）——我认可这个判断，这属于"查了之后确认没问题"，和"没查就放过"性质不同。

### 2.3 §6 配对专项 + P1-7 —— 真问题，定级准确

### 2.4 §9.1 PoC 草稿 —— 实用，4 条都可落地

逐条评估：

## 3. 仍存瑕疵（不阻塞，供 v3 或整改时注意）

### 3.1 P1-3 对 R1 建议的反驳成立，但整改方案仍有缺口

作者反驳"不能只机械替换 core.AtomicWriteFile"是对的——我核实该原语确实没做目录 fsync。但 v2 的整改只列了"在副本上完成变更，原子写盘成功后再替换内存快照"，**没给出 memory-before-disk 的具体实现模式**。这里有个微妙点：Go 里实现"原子写成功才改内存"需要先深拷贝 store、写副本、写盘、最后 swap 指针，且整个序列要在同一把锁内。建议整改方案补一句约束："变更全程持锁，先操作副本再写盘，写盘失败丢弃副本，成功后原子替换 `*FileDeviceStore.mem` 指针。"否则不同实现者可能写出仍有 TOCTOU 的版本。

### 3.2 P2-9 与 P1-7 的关系可以更明确

P2-9（Relay claim first-writer-wins）和 P1-7（手动码枚举 claim）都是"claim 抢占"，但分属 Relay 路径和直连路径，定级一 P2 一 P1。差异理由散落在两处：P1-7 是"无需任何凭据即可发起"（攻击者 B），P2-9 是"需要 QR capability 泄漏"（更高门槛）。建议在 P2-9 开头加一句交叉引用："与 P1-7 同属 claim 抢占，但因需 QR 泄漏、门槛更高，定 P2。"提升可读性。

### 3.3 §13 评级表缺一列"整改后预期"

R1 建议过"维持 C 并补整改后预期，或直接给 D"。v2 直接给了 D，但没给"整改后能回到什么"。§13 末尾的正文写了"完成第一批整改后可重新评估至 B-/C+"，但表格本身没有这列。建议表格加一列"整改后预期"，让评级变化路径更直观，也避免 D 这个分数让读者误以为"项目质量差"而非"当前未加固"。

### 3.4 风险统计数对账

复核：P0×1（P0-1）、P1×7（P1-1~P1-7）、P2×9（P2-1~P2-9）。✅ 与正文标题、§1 统计表完全对账。表扬——多轮修订后仍保持计数一致，说明修订纪律好。

## 4. 补充建议（超出 R1 范围）

### 4.1 建议增加"整改验收 checklist"

v2 有整改顺序（§11）和 PoC（§9.1），但缺一个**可勾选的验收清单**把两者绑定。建议加一节：

```text
发布前必须全部 ✅：
[ ] P0-1: read_file 拒绝 workspace 外路径（TestReadFileRejects... 通过）
[ ] P1-1: 入站帧 > 1MiB 被关闭（TestBridgeRejects... 通过）
...
[ ] CLAUDE.md:165 已更新，删除 /tmp 轮转假设
[ ] 错误码表 §10 的 code 已在代码中统一使用
```

这样发布负责人可以照着勾，不用在 §9/§10/§11 三节间来回跳。

### 4.2 建议明确"谁的 token，谁的责任"边界

威胁模型定义了攻击者，但没定义**凭据生命周期责任**。例如 device token 泄漏后，是 Mac 用户负责吊销（现状），还是应有自动轮换？management token 泄漏后呢？这影响"是否需要加自动轮换机制"的整改优先级。建议 §8 安全模型补一小节"凭据轮换与吊销责任"，明确哪些是用户操作、哪些应自动化。

### 4.3 P1-7 的整改可考虑更省力的选项

P1-7 整改列了 5 条（三层限流 + 失效 + 提码长 + UI + 连接资源），比较重。对内测阶段，一个**更省力的等效止损**是：手动码 claim 时强制要求同时提交 pairing ID（即取消"manualCode 单独查找"这条路径，`pairing_handler.go:175-176`）。这样手动码从"查找 secret"退化为"二次确认因子"，枚举攻击直接消失，限流变成兜底而非主防。报告可以考虑把这个作为"最小止损"列入整改，与完整限流方案分级。
