## 三、新发现

### F7【高】P2 首要论据 "78 func → 88 func" 是计数口径伪象

brief 第 172 行（P2"原因"首条）：

> gap analysis 的治理信号不是 `BridgeProvider` 1967 行本身，而是它被识别为 god-object 后**仍从 78 func 增到 88 func**；

第 9 行"god-object 仍在长肉"也依赖同一论据。

**实证（2026-07-04，iOS `main`）**：

```
# BridgeProvider.swift 不同计数法
全部 'func ' 行             : 88
排除 'private func'         : 59
排除 'private/static/@objc' : 43
# 无任何标准口径能复现 "78"

# 评估时点（2026-07-03）最近一次触碰 BridgeProvider.swift 的 commit
git log --before='2026-07-03T23:59:59' -1 -- .../BridgeProvider.swift
→ 05c30d92  2026-06-29  Fix airplane-mode reconnect storm + wake recovery

# 该 commit 下 BridgeProvider.swift 指标
全部 'func ' 行 : 88
总行数          : 1967

# 当前 main（HEAD）
全部 'func ' 行 : 88   总行数 : 1967   （与 06-29 完全一致）
```

**结论**：BridgeProvider.swift 自 **2026-06-29 到现在（07-04）零改动**，07-03 评估时它就是 88 func / 1967 行。"78 方法"是第一轮评估用了某种更窄的计数口径（推测排除了部分 `private`/`override`），gap-analysis 改用 `grep 'func '` 得到 88，把这个**口径差**误读成了**真实增长**。

这与 r1 F1 删除的 web "2→4 漂移"是**同一类错误**：跨文档计数比较、口径不一致、误当增长。但 r1 修订只对 web 应用了"不可复现就删"的纪律，P2 仍保留被证伪的 "78→88"。若施工/完成报告照抄此数字，会被任何复核立即打穿 —— 正是 r1 刚刚消除的风险，在 P2 上又留了一个。

**影响**：

- 不影响 P2 是否值得做：BridgeProvider 是 1967 行 / 88 func / 34 ForTesting 的 god-object（**全部复现**），冻结其体积的 gate 价值不变。
- 但"还在长肉"的紧迫性论据失效。讽刺的是，gate 的真实价值反而**更清晰**了：文件目前静态但无门禁，而它历史上是连接特性的下沉点（近 6 次 commit 全部触碰它，仅 06-29 一次就 +125 行），下一次 bridge 特性提交随时可能再长。

**建议**：把第 172 行（及第 9 行）的论据从"还在增长"改成"静态 god-object + 历史下沉点 + 无门禁"。可直接用的措辞：

> gap analysis 的治理信号不是 `BridgeProvider` 1967 行本身，而是它是连接特性的历史下沉点（近 6 次 commit 全部触碰它，2026-06-29 一次 +125 行），目前 88 func / 34 ForTesting、无任何净增长门禁。体积冻结比直接拆分成本低，能在下一次特性提交悄悄长肉前先建立防线。

这样 P2 论据完全建立在可复现事实（1967 / 88 / 34 + commit 历史）上，不再依赖被证伪的增长 delta，且说服力不降反升。
