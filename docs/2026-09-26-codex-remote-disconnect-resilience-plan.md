## 1. 摘要与范围

### 现状问题（owner 原话）

> 「codex-remote 对网络要求太高，网络有一点波动，就是无法加载会话投影。」

复盘证据（think.md，两仓）：
- macbridge `think.md:2-6`（2026-09-26）：Desktop 26.924 升级打断 codex-remote，iPhone 报「加载失败：codex-remote: stream closed」+「已配对，等待 ChatGPT Desktop」横幅；`watchBinding` 把所有恢复错误折叠成笼统文案。
- cordcode-ios `think.md:432`（2026-09-20）：Mac 端 codex-remote 自 11:36 起病态（thread/list 每轮 12s 超时、stream idle/closed、pairing 流反复重连），**至 14:00 未恢复**——驱动长时间不自愈的实测。（行号按方案记录来源 bd46169 框架；当前 iOS main fe421cdc 下同内容位于 :477——r2 报告 R2-A4② 亲核的双框架注记，v1.4 顺手补录。）
- macbridge `think.md:421`（2026-09-14）：error 通知风暴期间 live catalog attach failed 318 次，iOS 间歇卡「执行中」。

### 目标行为（R）

- **R-1** 网络瞬断（秒级~分钟级）期间与恢复后，iOS 打开 codex-remote 会话不再出现不可重试的硬错误「无法加载会话投影」；瞬态失败进入自动重试，驱动恢复后自动收敛。
- **R-2** 断线窗口内终结的 turn，重连后自动收口（不再永久停在 running、不依赖用户手动重开会话触发冷校准）。
- **R-3** 长连接期间 controller token 到期前主动续期，消除「到期→连接死亡→走完整重连」的额外不可用窗口。
- **R-4** 入站事件缺口可检测（per-stream seq 单调性——**信封级**：消息与 pong 共用同一计数器（v1.8 修正，F-R8-1）；chunk 信封共享所属消息的 seq_id，见 §2.2），缺口触发受影响会话的权威对账，不静默丢失。
- **R-5** driver 断线/恢复状态在桥内可区分、可查询（真实错误类别不再折叠为单一文案），为后续 iOS 推送立项预留钩子。

### 非目标

- **不做 controller 腿 cursor 重放**：官方协议不提供（E-1，源码 + owner attempt-008 双证）。维持 owner 方案 Gate P0 的 fail-closed 裁决（plan:588-599），不广告、不伪造。
- **不做 `backend_status_changed` 跨仓推送**：macbridge `think.md:45`（2026-09-26）已裁「待立项（协议面）……另立」。本方案只做 driver 侧状态暴露（S-6）。
- **不做 ACK 未确认发送缓冲/重传**：官方未提供 controller 侧重传语义（E-1/E-2）；出站失败由现有重连+重订阅路径兜底，重传缓冲收益低、复杂度高。
- **不处理官方 iOS controller 共存 / HTTP 409**：owner 方案任务 7 遗留缺口（plan:597），独立问题。
- 不修改官方 App / relay / 协议；不新增第二真相或第二 writer（SSV2 护栏）。

### 验收标准（行为级）

1. 受控断线（断 relay 链路 10–60s 后恢复）期间冷开会话：iOS 显示 loading/可重试态，恢复后 ≤ 一轮重试内自动加载成功，全程无硬「无法加载」。
2. 断线窗口内完成的 turn：重连完成后 ≤ 一轮对账内收口为完成态（真机时间线可见，无需重开会话）。
3. pairing revoked（401/403）仍为硬错误（提示重新配对语义），不被自动重试掩盖。
4. 入站 seq 缺口在桥日志可查，并触发对账；无缺口时零开销。

## 3. 设计与决定

### 3.1 S-1 恢复窗口拉取语义（跨仓，桥先行）

**S-1a（桥）终态/瞬态分类**：`markHydrateFailed` 的 `retryable` 参数目前对 `source_inspection_failed` 一律 `true`（`handlers_projection.go:603-605`），把「pairing revoked/无身份」「backend 未挂载/能力缺失」和「恢复中/传输抖动」混为一类。改为按错误源分类（v1.2 补全枚举，F-4）：
- `ErrNotConfigured`（无持久化身份或 phase=failed，`agent.go:110-119`）→ `retryable=false`（终态，iOS 显示硬错误，保留「请重新配对」语义）；
- `errProjectionSourceUnavailable`（`handlers_projection.go:430` 定义；codex-remote 路径返回点 `:852` agent 未挂载且 `ProjectionTurnCount==0`、`:876` 缺 `RichHistoryProvider` 能力断言）→ `retryable=false`（**v1.2 显式归类**：静态条件而非网络态——backend 未挂载/能力缺失在本次连接周期内不会自愈，S-1b 接上标志消费后会变成无限空转重试，属行为回退；与 revoked 同为终态类）；

- ctx 取消/其余意外错误 → `retryable=true` + 沿用既有 `RetryAt` 同 revision 退避（2026-09-13 think.md 修复已建立；kernel `MarkFailed` 内 `RetryAt` 计算 `projection_kernel.go:940-942`）。

分类改动**只落在** `source_inspection_failed` call site（`:603-605`）；mid-hydrate 各落点维持 `retryable=true` 不变（瞬态类）：`source_read_failed`（`:1079-1083`）、`hydrate_queue_timeout`（`:1015`）、`bare_source_wait_failed`（`:1142`）、`commit_failed`（`:1157`、`:483`）。wire 侧无需新映射：kernel 失败记录的 `Retryable/RetryAt/Attempts` 已经由 RPC handler default 分支透传（`handlers_projection.go:161-173`，v1.4 行号精度修正，R2-A4①），iOS 看到的 code 统一为 `projection.hydrate_failed`（`:147`）。

**S-1b（iOS）接上标志消费**：`isRetryablePullError`（`ProjectionStore.swift:164-181`，v1.2 修正行号，F-6②）扩展为——`CCCodeBridgeError.retryable == true` 时返回可重试，code 白名单保留为无标志时的兼容路径（老桥/其他 backend）。revoked 与 source-unavailable 因 S-1a 已是 `retryable=false`，不会被自动重试掩盖。**v1.4（R4-A1 处置，选项 b）**：删除 v1.3「尊重 `retryAfterMillis` 作为灾难 loop 的初始等待」的承诺——灾难 loop 维持既有本地退避 1s→30s（`ChatViewModel.swift:477-494`），`retryAfterMillis` 维持已解码、不消费；理由与 OD-1 边界见 §7.3。

**数据流不变量**：不新增错误面、不改投影内容语义；只把「桥已判定的可重试性」如实传导到 iOS 的既有重试 loop。SSV2 无新增 writer。

### 3.2 S-2 重连后 turn 对账（v1.4 重写事务域：READY-safe 专用对账事务，F-R4-1）

对 `turnByThread` 非空的 thread（断线时有 in-flight turn 的小集合）逐个重拉权威摘要页，**只消费终态事实**：
- 权威拉取复用 `ReadColdHistory`（`history_paginated.go:871-941`；桥侧既有消费先例 `handlers_projection.go:1372-1385`。`readTurnsPage` 为 agent 包内私有、桥不可直达，故不另造窄接口）。对账只消费映射结果中的 (turnID, status)，内容丢弃。诚实成本注记：上游仍 in-progress 的 turn 会被 `mapColdPage` 走查 items 到 EOF（`history_paginated.go:832-852`），该内容对账同样丢弃——成本与冷开同价、仅发生在「对账发现仍在跑」的少见分支；
- 摘要显示 turn 已终结 → 收口该 turn（completed/failed 按权威 status），并同步收口 codec 侧 `turnByThread` 条目（否则已完成 turn 永久留在对账集合，每次重绑重复对账）；
- 摘要显示仍在跑 → 维持 running（不猜完成，SSV2 规则 7）；
- 对账失败 → 记日志，thread 留在对账集合，下一轮 3s 周期重试（见下方接线），不新增定时器。

**为什么不能复用既有 hydrate admission（v1.4 亲核补证，F-R4-1 证据链）**：codex-remote 的 hydrate source 是 pathless（`ProjectionSourceDescriptor{Identity, Path:"", Cursor:0}`，`handlers_projection.go:876-881`）。对 READY 会话，`BeginHydrateTransaction` 在 `sourceChanged=false` 时直接返回 `AlreadyReady`（`projection_kernel.go:1020-1026`）——对账成为 no-op；要强制进事务只能 `sourceChanged=true`，但新事务的 reducer 从空起步（codex-remote 不在 `pathlessRichHistoryBackend` 名单 `:969-976` → `pathlessFullRebuildSource=false`，而唯一 restore 分支要求 `!sourceChanged`，`:1069-1083`），commit 时 `k.reducer.Restore(baseline)`（`:1357`）把 committed 投影**整体替换**为 tx baseline——而 `ReadColdHistory` 只返回最新一页（`:856-923`），**已 prepend 的旧页 turns 会被抹掉**。已证：既有 API 的两个分支（不强制=不对账；强制=page-1 rebuild 破坏完整时间线）均不可行，不得用 `sourceChanged=true` 的 page-1 rebuild 冒充增量对账。

**READY-safe 专用对账事务（拟议设计；owner/锁/fence/输入/commit API 逐项如下）**：
- **Admission**：kernel 新增 `BeginReconcileTransaction(backendID, sessionID) (ProjectionHydrateAdmission, error)`——`k.mu` 下要求 Phase==Ready（否则返回错误，调用方回落既有 hydrate 路径）；复用既有 `projectionHydrateTransaction` 结构体构造 tx：`source` 原样携带 `session.committedSource`、`startCut = session.committedSourceCursor`（commit 写回 `:1393-1394` 时因此保持不变——对账不移动 source cut）、`reducer = NewProjectionReducer()` 后 `Restore(committed snapshot)`——**以当前 committed 投影为 baseline**，older-window turns、goal/detail manifest（TurnProjection 全字段随 committed 快照序列化——per-turn detail manifest 字段 `DetailLoadState`/`DetailReasonCode`/`DetailInline` 定义于 `projection_types.go:221-226`；**v1.5 修正锚点（F-R5-A2）**：v1.4 所引 `projection_reducer.go:377-381` 实为 upsertTurn merge 分支收尾、无 manifest 字段）全部在 baseline 内保留；`coldArmedTurnIDs` 置空、`liveArrived` 信号就绪；随后与 hydrate 同序安装 `session.status=Hydrating / session.hydrate=tx / hydrateDone`（`:1092-1095`）。**不新增锁、不新增 fence 机制**——`IngestLive` 的既有 fence 分支（`:1203-1211`）自动把窗口期 live 事件深拷贝排队为 `pendingLive` 并返回 Deferred，无需改 `IngestLive`。
- **输入事件（只允许权威终态更新；经既有 `ApplyHydrateEvent` `:1160` 应用到 tx-local reducer）**。producer 侧过滤规则（ghost-turn 防护）：
  1. baseline 中存在且非 terminal、摘要中 terminal 的 turn → 发一条终态事件：completed → `turn_completed`；failed → `turn_error`；interrupted → `turn_aborted`（三分支逐项镜像冷路径 §9.2 封口纪律 `handlers_projection.go:1572-1576`/`:1693-1718`——同一 turn 冷开与对账必须收口为同一终态，aborted 与 error 客户端渲染不同（`projection_reducer.go:2407-2417` 终态保留注释）；不造新事件词表。**v1.5 修正（F-R5-A1）**：v1.4 所引镜像链 codec `decodeTurnCompleted` `codec.go:372-381` + `mapAgentEvent` 对非 completed 一律产出 `core.EventError` → 裸 `"error"` 事件名（`go-bridge/events.go:221-228`；reducer 无 `"error"` case，本轮 grep 亲证），既非 `turn_error` 也不构成封口词表依据，改引冷路径真值源；`upsertTurn` 对已存在 turn 是 merge 语义、内容保留，`projection_reducer.go:336-376`）；

### 3.3 S-3 入站 seq 缺口检测与去重

`readLoop` 按 per-stream 维护**信封级高水位游标** `(lastSeq, lastSeg)`（`lastSeg` 为 chunk 的 `segment_id`，plain 消息与 pong 为空）。**v1.8 修正（F-R8-1）**：官方 pong 与消息共享同一 per-stream seq 空间并计入 host outbound buffer（`client_tracker.rs:222-242`/`:273-287` 两条 pong 路径入单一 server_event 通道 `websocket.rs:410`，writer loop `:990-1067` 对通道内一切信封无条件 seq 分配并逐信封 `insert`（`:101-110` 无事件类型过滤）；本仓 ping 周期 10s `ws.go:317` → pong 每 10s 一条）——**游标必须对一切携带 seq_id 的入站信封推进**；只在消息帧推进会让每条 pong 的 seq 被跳过、下一条消息恒触发假「缺口」（每流每 10s 一次，系统性破坏 §1 验收 4「无缺口时零开销」，真缺口信号被噪声淹没）：

- **去重（v1.2 重写，F-1；判定表对 plain、chunk、pong 三类信封分别可判定——pong 为 v1.8 补，F-R8-1）**：信封按 `(seq_id, segment_id)` 游标判定——
  - `seq_id < lastSeq` → 重复（旧信封重放，plain/chunk/pong 同判）；
  - `seq_id == lastSeq` 且 `lastSeg` 为空（上一条为 plain 或 pong）：再遇 plain/pong → 重复（同信封重放）；遇 chunk → 理论不可达（官方一条消息要么整体要么全 chunk，`segment.rs:327` 二选一），记异常日志并按非重复处理（fail-visible，不静默丢弃）；
  - `seq_id == lastSeq` 且 `lastSeg` 非空（上一条为 chunk）：chunk `segment_id <= lastSeg` → 重复（同消息已见 chunk 重放）；`segment_id > lastSeg` → 新 chunk（接受，更新 lastSeg）；遇 plain/pong → 理论不可达，同上异常处理；
  - `seq_id > lastSeq` → 非重复：`== lastSeq + 1` 正常推进（plain/pong 置 `lastSeg` 空 / chunk 置 `lastSeg`），`> lastSeq + 1` → 信封级缺口（见下）；
  - **pong（v1.8 补，F-R8-1）**：`seq_id > lastSeq` → 非重复、正常推进并置 `lastSeg` 空（pong 无 segment；pong 恒为新 seq——官方 writer loop 单队列串行分配、每 seq 唯一归属一个信封（`websocket.rs:1029-1067`），不命中上两类「理论不可达」混合帧型分支）；`seq_id <= lastSeq` → 重复（host 重连重放携带原 seq，与 plain 同判跳过）。

  游标比较语义镜像官方 ack 清除路径的 `(seq, segment_id.unwrap_or(usize::MAX))` 游标（`websocket.rs:112-138`）。**v1.1 的「`seq_id <= last_seen` → 跳过」按字面实施会把大消息（>150KB 拆分）第 2..n 个 chunk 当重复丢弃、重组永不完成——已证错误，废除**；v1.1 所引镜像源 `client_tracker.rs:134-143` 是 client→host 方向、仅 `ClientMessage` 分支（chunk `:221` 直通），不可平移，v1.2 改引 ack 游标语义。
- **缺口检测与归属（v1.4 重写，F-R4-2；一并闭合 R2-A1；v1.8 改信封级，F-R8-1）**：**信封级**——`seq_id > lastSeq + 1` → 记录缺口范围 `(lastSeq+1, seq-1)` **一次**，随后高水位游标**立即推进**到该帧（`lastSeq = seq`，`lastSeg` 按帧型置位，同「正常推进」规则）——不推进则缺口后每帧重复触发（R2-A1 指出、r4 升级为阻塞）；每个真实新缺口（后续再出现不连续）是一次新事件，会再次触发——正确。缺口语义 = **任意信封丢失**——可能只是一条无害的 pong（不触达任何投影语义；无法从缺口后首帧推断丢失帧型，与无法推断 thread 归属同因），维持 fail-visible：日志如实标注「缺口可能为 pong 或消息」，fan-out 处置不因帧型猜测分叉。缺口是 **stream 级未知归属事件**：transport `Envelope` 只有 client/env/stream/seq 与 payload、不携带 thread 身份（`envelope.go:32-49`），缺失 seq 的 payload 已不存在，无法从缺口后首帧推断丢失事件所属 thread（chunk 帧重组前甚至没有可解析 JSON-RPC payload，`stream.go:409-420`）。处置：
  - **有界 fan-out**：缺口 → 该 stream 的 observed 集 ∩ `turnByThread` 非空的**全部** thread 加入 S-2 对账 pending 集（与 attach 触发共用同一信号 seam，幂等并集；对账成功后 `turnByThread` 条目清除（§3.2），不会反复进集）。例：thread A 的 `turn/completed` 丢失、下一帧属 thread B → A 与 B（若 B 也在 observed∩turnByThread 中）都进对账集——A 必被覆盖，不依赖错误归属。
  - **无在飞 turn 的 thread**：只记日志（缺口范围 + observed 清单），不进对账集——对账只能修终态，无在飞 turn 无可修对象；缺口内内容级丢失的既有恢复路径 = terminal turn 的 detail lazy 重载（`turn_detail_lazy/chunks_v1` 既有机制）+ 冷开 page-1 重建。诚实边界：不静默，也不伪造恢复。
  - **replay 取舍（诚实边界）**：缺口后 host 侧重放（E-11：host 重连重发未 ack 信封，携带原 seq）会被 `(seq,segment)` 游标判为重复丢弃。终态丢失由 fan-out 对账补偿；缺口内**内容级**丢失不从 replay 恢复——考虑过的替代（记录 gap range、range 内 seq 视为未应用而接受重放）被否决：已终态 turn 的迟到内容在 reducer 的应用行为不是已验证安全路径，接受重放需新的 reducer 保证、扩大范围；损失由 lazy 重载/冷开重建兜底。残余登记 §6 风险 3。
- **chunk ack 补 `SegmentID`（v1.2 新增子项，E-12，超出 r1 意见范围；r2 已确认采纳）**：ack 构造（`stream.go:390-407`）对 chunk 信封补 `SegmentID: env.SegmentID`（字段已备，`envelope.go:45`），对齐官方协议文档（`protocol.rs:114-119`：chunk ack 携带 segment_id，sender 只保留未 ack 的 wire chunks）。不修则首 chunk ack 等价 `(seq, MAX)` 游标提前清除整消息缓冲（`websocket.rs:123`），host 腿中断丢消息尾部且**不产生信封级缺口**（chunk 共享所属消息的 seq）——缺口检测的已证盲区；修复后未送达 chunk 保留在 host 重放缓冲，与缺口检测共同覆盖 R-4「不静默丢失」。
- **pong 信封到达即 ack（v1.9 新增子项，F-R9-1）**：pong 分支（`stream.go:307-316`）在 `markHostActivity` 后对携带 `SeqID` 的 pong 调用既有 `s.ack(env)`（构造同 `:390-407`，无 `SegmentID`——官方 `websocket.rs:123` 语义下 `(seq, MAX)` 游标恰好清除该 pong 及更早一切已收信封；pong 无 segment、单连接流内有序故被清除者均已收到，语义安全，与既有 plain 消息 ack 同型；重放 pong 同样到达即 ack——幂等清除，host 重连重放后再次清空该 seq 前缓冲）。经 `ack()` 既有 `acksDisabled` 早退（`:397-399`）：熔断 open/half-open 期间 pong 不逐条 ack，由 probe ack 按最高游标顺带清除（§3.7），窗口内累积 ≤⌈T/ping 周期⌉ 条有界，§3.7 噪声上界推导不变。**依据**：pong 计入 host outbound buffer 且清除仅 client Ack 一途（E-11；官方 ack 语义覆盖「all server envelopes…≤seq」，`protocol.rs:116-119`），本仓 ping 为自加策略（10s，`ws.go:317`；官方开源仓无信封层 ping/ack 参考实现——`ClientEvent::Ack` 构造仅 tests.rs:1650、`ClientEvent::Ping` 仅 host 侧 match arm，grep 亲证），累积后果由本仓 controller 设计承担。**不修的已证后果（楔死场景，r9 F-R9-1）**：transport 存活而 app-server backend 楔死（RPC 无响应；方案自引 2026-09-20 事故 `ios think.md:477` 即此形态：连接在、`thread/list` 每轮 12s 超时、2.5h 不自愈）时，pong 是唯一入站流量——`PongStatus` 仅客户端注册语义（注册即 Active `client_tracker.rs:179`、已知客户端 Ping 恒回 Active `:225`、Unknown 仅未注册客户端 `:233`），本仓 `stream.go:311` 判死不触发——且无消息信封、无消息 ack（消息 ack 由 3s catalog 循环 RPC 响应保证，`main.go:1046-1066` → `session.go:335` `thread/loaded/list` → 响应经 `:324` ack；RPC 响应非 transport 层产物，楔死即停）→ 未 ack pong 每 10s 一条**无界累积** → ~21.3 分钟填满 128 全局容量（`transport/mod.rs:24`）→ writer 全局反压停摆（`websocket.rs:996`）→ pong 停达 → 本仓 60s 静默判死重连（`ws.go:318`）→ 被弃 stream 的 pong 无任何清除路径（E-11）→ 全局容量永久占用、后续所有 stream 零入站 → **永久重连循环直到 Desktop 重启**——§6 风险 5 停摆模式的第二触发路径（无 sentinel、无熔断参与），把「backend 楔死、解楔后可自愈」的可恢复故障升级为重连不可愈的不可恢复停摆（r8 §6.2③ 对「空闲流 pong 累积」的排除以「3s catalog 循环保证消息帧到达」为前提，仅在健态成立）。修复后未 ack pong 在途 ≤1 条（closed 态到达即清）**无条件成立**——不依赖 catalog 循环 RPC 响应健康；楔死期间 transport 存活、RPC 失败维持 S-1a 瞬态分类，解楔后自动收敛。E-12b 不新增样本项（pong 帧 wire 形状由样本集⑥覆盖、ack 回程形状由③覆盖——r9 §7 裁定）。

不重传、不断线、不伪造事件——fail-visible 而非 fail-closed。依据：host→controller 方向 `ServerEnvelope.seq_id` 按 `(client_id, stream_id)` **信封级**严格单调（官方 `websocket.rs:1031-1067`——消息与 pong 共用计数器，v1.8 修正 F-R8-1），信封级缺口即真实信封丢失（可能为无害 pong，见上）；chunk 级丢失由 ack 形状修复消除（E-12——源码语义 E-12a verified；部署 wire 形状 E-12b **pending**，S-3/S-7 实施被其门住，见 §4）；pong 级滞留由 pong 到达即 ack 消除（v1.9，F-R9-1——不依赖消息 ack 持续到达，楔死 backend 场景累积上界仍 ≤1 条）。

### 3.7 S-7 ack 熔断器有界化（v1.2 新增，F-2 对策升主链；v1.4 重写状态机，F-R4-3）

**现状**：熔断器激活后本 stream 生命周期内停发一切 ack（`stream.go:359-373` armed → `ack()` `:397-399` 早退），无有界时长、无最低频率。熔断职责是停掉 2026-09-14 事故的 ack→sentinel-error→ack 自激风暴（750/s，`think.md:415-425`），不是停 buffer 排空——但无限期停 ack 会让 host 侧缓冲只增不减，与全局反压叠加成整腿永久停摆（§6 风险 5）。

**v1.4 先删一个伪事实（F-R4-3 亲核）**：v1.3 的「transport 接受 → 恢复正常逐信封 ack」**不可观测**——relay ACK 只证明 relay 收帧、不证明 app-server 接受（`stream.go:44-47` 本仓既有注释）；client ack 无 host 成功响应；sentinel 只是异步**负向**信号。协议无可靠正向确认，任何 in-stream「解除」判定都是在猜。

**状态机（拟议设计；per-Stream，连接作用域；全部可被 fake conn + fake clock 判定）**：
- **closed**（`acksDisabled=false`）：逐信封 ack（现状行为）。
- **open**（`armedAt=now`）：不 ack 任何入站帧。入站帧到达且 `now−armedAt ≥ T` → 以 S-3 的 per-stream 最高已见 `(seq, segment)` 游标**发一条 probe ack** → **half-open**（`armedAt=now`）。
- **half-open**：不 ack 入站帧。sentinel 到达（**任意状态**均如此）→ **open**（`armedAt=now`，T 重新计时）。入站帧到达且 `now−armedAt ≥ T`（即上一 probe 后 T 内无 sentinel）→ 再发一条 probe → half-open（`armedAt=now`）。
- **probe 触发帧型（v1.5 补，F-R5-A3）**：上述触发 probe 的「入站帧」**含 pong 控制帧**（readLoop 收 pong，`stream.go:307-314`；本仓 ping 周期 10s，`ws.go:317`）——熔断 open 且无数据流量的静流场景下 pong 是唯一入站帧流，计入后 host 恢复接受时缓冲仍以 probe 节奏排空（严格优于等下一条数据帧）；ack 帧不参与（readLoop 对 `typeAck` 直接 `continue`，`stream.go:305-306`）。pong 计入不改变噪声上界推导（pong 亦为入站帧，probe 率 ≤ 1 条/T 不变）。
- **本 stream 生命周期内不回 closed**。「恢复正常逐信封 ack」的唯一路径 = 下一次重连的新 stream（既有语义：`stream.go:53-57`「Connection-scoped: a fresh stream re-arms so a server that later accepts acks regains the documented chunk-retention protocol」）。这是「唯一解除证据」的可判定表述：**in-stream 无解除，解除 = 流重建**——不依赖任何不可观测的接受推断。
- probe 期间普通入站帧：不 ack、不触发新 probe（T 窗口内）；probe ack 写失败沿用现状（`_ = s.conn.Write`，连接死亡由 readLoop/ping 判死路径暴露）。
- **T=30s 默认**（量级参照官方 refresh 失败退避 24–36s，`server_api.rs:27-28`；内部噪声上界的工程选择，非协议时序声明，不适用 plan:508-509 取样门——该约束针对依赖外部 ctrlExp 分布的 S-4 提前量）。无新增观察窗口常量——half-open 的出口由 sentinel 或下一 probe 周期定义。

**噪声上界（重新证明，不依赖接受假设）**：probe 只在 `age(armedAt) ≥ T` 的入站帧上发生，且每次 probe/sentinel 都重置 `armedAt` → 相邻 probe 间隔 ≥ T。2026-09-14 形态为 host 对每条 ack 恰回一条 sentinel（`think.md:415-425`）→ 稳态 sentinel 通知率 = **1 条/T**（事故形态 ~750/s → 1 条/30s），**无条件成立**。若上游形态变为 1 ack → N sentinel，上界按 N/T 缩放——S-6 暴露 probe/sentinel 计数器供漂移观测。

**缓冲排空语义**：每条被 host 接受的 probe ack 按最高游标清除该 stream 缓冲中 ≤ 游标的全部信封（官方 ack 清除语义 `websocket.rs:112-138`）→ 即便不回 closed，host 恢复接受后缓冲以 probe 节奏（每条 probe 至多 T 延迟）排空。**残余 ③（v1.4 新登记）**：host 恢复接受但本 stream 停留 half-open 时，重流量下 host 缓冲可在 probe 间隔内涨至全局反压门限 → writer 间歇停摆（每 128 信封批至多 T 延迟），下次重连消除；S-6 计数器可见。

**依赖（R2-A2 修正）**：S-3 的 ack `SegmentID` 子项（E-12）**与** per-stream `(seq, segment)` 游标维护（§3.3 去重状态）——两者共同构成 probe ack 的输入（无 SegmentID 则 `(seq, MAX)` 提前清除未送达 chunk，见 §3.3；无游标则 probe 无最高水位可发）；S-3 其余部分（缺口 fan-out/对账触发）不构成 S-7 前置。**v1.8 注（F-R8-1；v1.9 补 closed 态分述，F-R9-1）**：游标含 pong seq——armed 态下 probe ack 按官方 `websocket.rs:123` 游标语义顺带清除 host 缓冲内未 ack 的 pong（与消息清除同型，正确），随 §3.3 修复自动一致；closed 态的 pong 由 §3.3 v1.9「pong 到达即 ack」子项逐条清除（经 `ack()` 既有 `acksDisabled` 早退，熔断语义优先、两态互不冲突），无需额外机制。

**完成断言（定向单测，fake conn + fake clock，八项）**：① closed 行为与现状逐字节一致；② open + `age≥T` + 首帧 → 恰一条 probe 且携带最高已见游标；③ probe 后普通帧先到（`age<T`）→ 该帧不被 ack、无新 probe；④ 连续积压 N 帧 → 恰一条 probe、零逐信封 ack；⑤ probe 后 sentinel 延迟到达 → 转 open、`armedAt` 重置、全程无逐信封 ack 风暴；⑥ 稳态拒绝循环（probe→sentinel→T→probe…）→ sentinel 数 = probe 数 = elapsed/T；⑦ 新 stream → closed；⑧ 静流场景（open/half-open + 无数据帧）pong 到达且 `age≥T` → 触发 probe（pong 计入触发帧型，F-R5-A3）。E-10 实施期真机观测 probe/sentinel 计数与停摆签名可见性（sentinel 风暴本身依赖上游 host 版本缺陷，真机不可控复现，行为验收以单测为准）。

**残余风险（诚实边界）**：① host 侧持续拒绝 ack（0.154.0-alpha.6.2 形态的上游缺陷）——probe 维持 1 条/T 噪声，缓冲排不了，停摆只能靠 Desktop 侧修复/重启；② 正常断线时在途未 ack 信封仍随被弃 stream 永久占用全局容量（host 侧无 client 关闭清除路径，E-11），单次量为在途窗口（消息在途通常 0–2 条 + 未 ack pong ≤1 条——v1.9 pong 到达即 ack 后**无条件有界**，不依赖 catalog 循环健康，F-R9-1；修复前楔死场景可达 128 条全局容量，见 §3.3 pong ack 子项），累计效应随 Desktop 存活时间增长——完整修复需官方 host 侧改动（非目标：不修改官方）；③ probe 节奏排空的重流量间歇停摆（上段，下次重连消除）。S-6 暴露熔断状态（closed/open/half-open）、probe/sentinel 计数与「反复 60s 零事件流死亡」停摆签名供诊断。
