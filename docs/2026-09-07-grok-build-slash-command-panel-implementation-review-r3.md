## 3. 剩余阻断与修改要求

### T1 · P1：CMU 可以先于 durable 确认翻转 chip，绕过新三态门

**位置：方案 §6.2.2、§6.2.3、§6.3、§7.2。延续 S1。**

现稿同时规定：读回超时则 RPC error、chip 不翻转；CMU 三路到达则直接更新 observed、同 epoch 同值去重。然而上游先更新 actor，再独立排队 persistence 与 CMU，二者没有“先写盘成功再通知”的保证。

可达顺序：收到 set plan → stdout CMU(plan) 到达 → observed 先把 chip 变橙 → plan_mode.json 未写成 → 读回超时、RPC error。没有成功 response patch 并不能撤销之前已经显示的 plan。所谓同值去重只能减少重复更新，不能把未确认状态变成已确认状态。

源码依据：上游 `xai-grok-shell/src/session/acp_session_impl/session_mode.rs` 的 `handle_session_mode`/`persist_plan_mode_state`，以及 `acp_session_impl/updates.rs:348` 的独立 event 入队。1.0.13 的具体形状仍由 P5/P7 验证。

**要求：**将本次切换的 observed 与 durable-confirmed 分开。事务待确认期间如何处理自有 CMU及其文件/leader 副本必须明确；未确认只显示 pending/unknown，不能表示持久成功。失败后也不能伪造反向状态或保持一个被命令结果否定的确认标识。若无法可靠关联通知与操作，必须用权威状态验证决定显示，不能凭 CMU 相同值假定是本次 ack。

**定向验证：**CMU 先到 + 读回超时；CMU 先到 + 成功读回；无 CMU 的幂等切换；待确认期间外部相反切换。四种顺序都不得用未确认值展示已成功切换。

### T2 · P1：到达序 last-wins 仍不能实现“旧通知/旧 response 晚到不翻回”

**位置：方案 §6.2.3、P5、Phase 2 验收、§10。延续 S3。**

v1.2 明示无全局序号时旧 live 可翻回，又要求可控注入单测证明“晚到不翻回”。这两个规则不兼容。例如先发生 plan、后发生 default，bridge 先收到 default、再收到延迟 plan；按到达序 last-wins，最终必为旧 plan。

同 epoch 同值去重只处理重复，不处理不同值的新旧。重订阅重基线只有发生重订阅才运行；用户停留在当前会话时，错误状态可持续存在，不能声称只是“一拍”。response 请求值 patch 也可能晚于外部更新，必须使用同一有效性规则处理。

**裁定：不接受此残差作为已完成的状态显示方案。** D2 已选择未知时中性，不能为了总有橙/灰值而展示无法判定的新旧状态。

**要求：**P5 若提供可比较身份/序号，落成确定顺序规则；否则选择单一有效观测来源和订阅代际，旧代际消息丢弃，切源前建立新基线，或者把通知用作权威读回的触发而非直接写最终状态。来源选择是实现判断，不需再问产品裁决。没有证明前，保持该状态更新能力的对应技术门阻断。

**定向验证：**plan→default 的通知逆序、旧代际迟到、旧 response 晚于新模式、hydrate 与 live 交错。测试须按实际所选机制断言结果，不能注入恰好按顺序的数据来证明乱序安全。

### T3 · P2：面板每次打开只重新请求 bridge，仍可永久拿到旧缓存

**位置：方案 §6.1 缓存规则与非原子边界。延续 S6。**

现稿规则是无 TTL、只在 bridge 重启/cwd 变化时失效，Mac 命中缓存即回。同时声称外部 plugins/skills 变化由“下一次面板打开的 list”反映，且“每次 turn/面板打开都会刷新”。没有 turn、cwd 不变、bridge 不重启时，无论打开面板多少次，通道 2 都不会被调用。外部变化因此无法被新一次 List 发现。

这不是官方目录与执行之间不可消除的瞬时竞争，而是 bridge 自己制造的无界陈旧窗口。

**要求：**定义一次明确的权威刷新时机。建议面板每次打开请求 List 时，Mac 真正拉取当前官方目录；若采用活跃会话缓存，必须有可证明的失效/更新来源。拉取失败就展示错误，不能回退旧表冒充刷新成功；无须另加每次 execute 二次拉取。官方空表仍整表替换。

**定向验证：**首开得到 A，外部目录改为 B，不发 turn/不重启/不改 cwd，再开面板必须得到 B（或真实获取错误），不能永远返回 A。
